# MaaleNex–IROKA Integration Contract v1.0

**Contract ID:** MN-IROKA-IFACE-001  
**Status:** Owner-authorized implementation baseline; external IROKA service binding pending  
**Version:** 1.0.0  
**Scope:** Backend service boundary only. No UI or frontend changes.

## 1. Purpose and authority

IROKA is MaaleNex's governed intelligence and assurance subsystem. MaaleNex remains the system of record and execution authority for passenger, operator, fleet, trip, booking, support, wallet, payment, delivery and cargo data.

IROKA may provide policy evaluation, risk classification, evidence-grounded assistance and recommendations. An IROKA decision is not permission to perform a business mutation. MaaleNex must independently authorize and execute every mutation through its existing domain service and transaction boundary.

This contract does not claim that a network-accessible IROKA service exists. The currently verified IROKA artifact is a Rust kernel/library with G01/G02 contracts; production service hosting, trust-root provisioning and a stable deployed HTTP endpoint are not established. Until that service binding is independently verified, the MaaleNex adapter MUST fail closed and MUST NOT silently substitute a local model or heuristic.

## 2. Trust boundaries

1. MaaleNex authenticates the caller and derives the actor and tenant from its own verified session. Caller-supplied actor or tenant identifiers are never authority.
2. MaaleNex sends only the minimum purpose-bound context to IROKA. Raw passwords, session cookies, payment credentials, full identity documents, unnecessary passenger PII and secrets MUST NOT be sent.
3. IROKA verifies its own service credential under G01 and applies its configured policy/governance under G02. A service identity does not itself confer capabilities.
4. MaaleNex validates the response binding to the original request, tenant, actor, capability, resource, policy version, expiry and correlation identifiers before considering it.
5. Missing, malformed, stale, mismatched, unauthenticated or unverifiable IROKA responses are unavailable/escalated; they never become ALLOW.
6. IROKA does not receive database credentials and has no direct database, object-storage, wallet-ledger or payment-provider access.

## 3. Request envelope

Every request is a versioned JSON object with:
- contract_id: MN-IROKA-IFACE-001
- contract_version: 1.0.0
- request_id: UUID generated by MaaleNex
- correlation_id: UUID shared with MaaleNex audit/trace records
- tenant_id: opaque MaaleNex tenant/organization scope, only where applicable
- actor_subject: opaque identifier resolved from MaaleNex authentication
- capability: stable action code, never a natural-language permission
- resource: opaque resource type and identifier
- policy_version: explicit MaaleNex policy version
- requested_at: UTC timestamp
- data_classification: PUBLIC, INTERNAL, CONFIDENTIAL or RESTRICTED
- context: minimized, schema-governed attributes only

The receiving service MUST reject unknown contract versions and unknown fields. Tenant and actor values are contextual bindings, not proof of identity. IROKA must authenticate MaaleNex's service credential independently.

## 4. Decision envelope

The decision response binds to the exact request_id, correlation_id, tenant_id, actor_subject, capability, resource and policy_version. It contains:
- decision_id: stable opaque identifier
- decision: ALLOW, DENY, REQUIRE_APPROVAL or ESCALATE
- reason_code: language-neutral stable code
- issued_at and expires_at: UTC timestamps with a short bounded validity
- audit_receipt_id: IROKA audit correlation reference
- evidence_refs: opaque references only; no untrusted executable content

A response must be authenticated and integrity-protected by the agreed service transport/credential profile before production use. A bare JSON ALLOW is never sufficient. MaaleNex must reject a response whose request binding differs, whose expiry has passed, whose policy version is stale, or whose audit receipt is absent.

## 5. Decision semantics

- ALLOW: IROKA's advisory/governance evaluation passed. MaaleNex still runs its own authorization and domain invariants.
- DENY: MaaleNex rejects the requested action and records the decision.
- REQUIRE_APPROVAL: MaaleNex pauses the action and routes it through its independently authenticated approval process. No action is queued for execution.
- ESCALATE: MaaleNex blocks the action and requires human review.
- Timeout, service absence, invalid signature, unknown key, revocation uncertainty, malformed response or contract mismatch: fail closed as unavailable/escalated.

No decision may directly execute an action, issue a payment, change a fare, publish a route, confirm a booking, release a wallet hold, alter operator status or grant staff permissions.

## 6. Idempotency, retries and audit

Requests that can be retried include an idempotency key scoped to tenant, capability and resource. The same key with a different payload is a conflict. Retries must reuse the original request ID and idempotency key. MaaleNex records request ID, correlation ID, contract version, decision code, reason code, policy version, IROKA receipt reference and adapter outcome. Audit records must not contain secrets or raw sensitive payloads.

A timeout is an unknown remote outcome, not proof that the remote service did not process the request. MaaleNex must not repeat side effects; the IROKA decision operation is read-only and must be idempotent.

## 7. Availability and degradation

The adapter is disabled by default until an authenticated endpoint, service identity, trust roots, revocation behavior, response integrity profile, timeout budget and operational owner are verified. When disabled or unavailable, only workflows explicitly classified as safe for non-IROKA operation may continue under MaaleNex's own policies. High-risk or IROKA-required workflows must fail closed.

No local LLM, third-party provider, alternate AI service or unreviewed heuristic may be silently substituted.

## 8. Versioning and compatibility

Breaking schema or semantic changes require a new contract major version and a compatibility plan. Additive fields are not accepted until the negotiated contract explicitly permits them; v1.0.0 uses strict schemas. Both systems must publish tested fixtures for valid, invalid, expired, mismatched, replayed and unavailable cases.

## 9. Implementation and release gates

The initial MaaleNex implementation supplies immutable request/decision schemas and a disabled fail-closed gateway. It deliberately does not invent an IROKA HTTP route or pretend a network call has succeeded.

Before enabling transport:
1. verify the IROKA service interface and deployment artifact;
2. agree and implement service-to-service credential issuance, audience, key rotation and revocation;
3. verify response integrity and replay controls;
4. map IROKA capabilities to MaaleNex permissions and domain policies;
5. implement bounded timeout/retry and circuit-breaker behavior;
6. run cross-repository contract tests against the exact IROKA revision;
7. provision secrets through a protected runtime channel;
8. complete independent security review and Owner authorization.

No merge, deployment, production key provisioning or activation is implied by this contract.
